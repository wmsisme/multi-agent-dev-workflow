# multi-agent-dev-workflow

> 用**多智能体协作**替代「一个人 + 一个对话窗口」干脏活累活：一个主 Agent 当编排器，若干专职子 Agent 各管一件事，每个子 Agent 只拿自己需要的上下文、只干自己那一段。
>
> 本仓库是一个**真实多智能体编制（agent roster）的公开导出**：完整提示词 + 角色边界 + 编排规则 + 安全阈值。
> **说明**：所有提示词字符串均可直接复用；仓库**不含**任何编排引擎、框架或运行时（见「我到底开源了什么」）。

---

## 这个编制解决什么问题

一个「**生成 → 评测 → 定位失败根因 → 补资料 → 重新生成**」的迭代闭环，人工做有两个绕不过去的痛点：

1. **口径会漂**——同一个人今天和明天打分标准不一致，跨轮次的结果没法比较；
2. **判断很贵**——"这次失败是检索没召回、还是模型自己编的"，需要语义判断，写成 if-else 写不动。

把这两件事交给专职 Agent，并且**让每个 Agent 只干一件事**之后，闭环就能自动跑起来。

## 架构：主 Agent 编排 + 8 个专职子 Agent

```text
                        ┌───────────────────────────┐
        用户任务 ───────▶│  主 Agent（编排器）        │
                        │  拆解 / 派活 / 定序 / 整合 │
                        │  质量回检 / 安排返工       │
                        └───────────┬───────────────┘
             ┌──────────────┬───────┴───────┬──────────────┐
             ▼              ▼               ▼              ▼
      ┌────────────┐ ┌────────────┐ ┌────────────┐ ┌────────────┐
      │ rag-       │ │ generate-  │ │ generate-  │ │ failure-   │
      │ controller │ │ question   │ │ score      │ │ case-      │
      │ 调用管控    │ │ 测试题生成  │ │ 定量评分    │ │ analyst    │
      └────────────┘ └────────────┘ └────────────┘ │ 根因诊断    │
      ┌────────────┐ ┌────────────┐ ┌────────────┐ └────────────┘
      │ rag-       │ │ generate-  │ │ generate-  │ ┌────────────┐
      │ knowledge- │ │ docx       │ │ workflow   │ │ 角色提示词  │
      │ writer     │ │ 文档生成    │ │ 编排调度    │ │ 转换器      │
      └────────────┘ └────────────┘ └────────────┘ └────────────┘
```

**核心设计原则**（也是和「一份提示词里塞所有要求」最大的区别）：

| 原则 | 做法 | 为什么 |
|---|---|---|
| **职责单一** | 一个子 Agent 只干一件事，出题的不管评分，评分的不管补资料 | 防止"运动员兼裁判"——Agent 会倾向于给自己打高分 |
| **上下文隔离** | 每个子 Agent 有独立上下文，看不到别人的中间过程，只接收主 Agent 显式传入的任务 + 材料 | 一是省上下文，二是防止上一步的偏见污染下一步 |
| **工具边界** | 每个子 Agent 声明自己能用的工具清单 | 限制爆炸半径，也压缩它的行为空间 |
| **控制流由模型决定** | 主 Agent 读上一步返工结果再决定下一步，不是把固定 Prompt 链写死在代码里 | 见下文「和顺序调 Prompt 的区别」 |

## 和「按顺序调 8 个写好的 Prompt」有什么区别

这是最常被问到、也最容易被质疑的一点：

- **固定 Prompt 链是死的**：第 4 步无论结果好坏都会走到第 5 步；
- **这里的控制流是运行时决定的**：评分不过关 → 主 Agent 安排返工或换 Agent 重做；诊断出是"检索遗漏" → 主 Agent 把任务派给知识库写入 Agent 补充资料，然后回到复测。

也就是说，**编排器的职责不是"按顺序发消息"，而是"读结果、做判断、决定下一步和要不要返工"**。

## Agent 清单

| 子 Agent | 职责 | 何时被调用 | 提示词 |
|---|---|---|---|
| `generate-workflow` | 多 Agent 编排：任务拆解、Agent 匹配、工作流调度、结果整合、质量回检与返工 | 复杂任务需要多个专职 Agent 协同 | [→](agents/generate-workflow.md) |
| `rag-controller` | 调用管控：封装调用、循环次数与耗时监控、评分趋势判断、异常中断保护 | 需要防死循环 / 控时长 / 防评分停滞 | [→](agents/rag-controller.md) |
| `generate-question` | 测试题生成：多类别成组出题，每题标注"答案必须包含的关键点" | 需要成套、可核对的测试题 | [→](agents/generate-question.md) |
| `generate-score` | 定量评分：检索阶段（上下文相关性 / 召回率）+ 生成阶段（忠实度 / 答案相关性 / 关键词 / 标准答案吻合） | 需要客观可复现的评分、或对比两个输出 | [→](agents/generate-score.md) |
| `failure-case-analyst` | 根因诊断：把失败归为「检索到无关内容 / 遗漏关键信息 / 模型幻觉」三类，给可执行修正建议 | 产出质量不合格时 | [→](agents/failure-case-analyst.md) |
| `rag-knowledge-writer` | 知识库写入：写前校验 → 分批写入校验 → 写后抽样检索验证 → 统计报告 | 要灌入新文档 / 更新条目 | [→](agents/rag-knowledge-writer.md) |
| `generate-docx` | 文档生成：把知识组织成成体系的文档 | 需要结构化长文时 | [→](agents/generate-docx.md) |
| `role-prompt-converter` | 把角色描述文字转成标准化的角色系统提示词 | 需要把散描述的"设定"变成可复用提示词时 | [→](agents/role-prompt-converter.md) |

## 安全管控：让 Agent 不失控

Agent 会死循环、会把成本烧光、会"自己骗自己"。这个编制里的四道闸（[完整说明](docs/safety-guardrails.md)）：

| 闸门 | 阈值 | 触发后 |
|---|---|---|
| 迭代上限 | 最大 **5** 轮 | 立即中断，返回当前最佳结果 |
| 总耗时 | **120 秒** | 超时中断 |
| 评分趋势 | 连续 2 轮提升 **< 0.01** | 判停滞，提前终止 |
| 评分下降 | 任何一轮下降 | 立即中断，**回退到上一轮最佳结果**（而不是把更差的结果交出去） |
| 循环模式 | 连续两轮输出余弦相似度 **> 0.95** | 判定在原地打转，直接中断 |

写入侧另有一条硬规则：**写前校验 → 写后抽样检索验证 → 写失败不留半写数据**。

> 中断不等于抛异常：停止时返回 `{最终结果, 监控数据, 中断原因}` 三元组，调用方永远能拿到东西。

## 快速开始

这套编制**不绑定框架**——任何支持「子 Agent / 子任务派发 + 独立上下文」的运行时都能落地：

1. **建子 Agent**：按 [`agents/`](agents/) 里每个文件建一个子 Agent，文件名即标识名，提示词用文件里「完整提示词」一节；
2. **声明调用时机**：把每个文件「何时被调用」一节填进子 Agent 的 **description** 字段——**这是编排器能不能正确匹配任务的唯一依据**，别省略；
3. **声明工具边界**：按「工具边界」一节给每个子 Agent 配工具，尤其是写入类和命令执行类工具；
4. **配主 Agent**：主 Agent 有两种做法——用框架自带的主 Agent（推荐先用它跑通），或把 [`agents/generate-workflow.md`](agents/generate-workflow.md) 作为专职编排 Agent 挂上；
5. **按场景裁剪**：不需要的 Agent 直接删掉，编排器读不到它就不会派活。

**实际配置（参考值）**：主 Agent 用**自建的 `generate-workflow`** 做编排（不是框架默认的那个）。一整轮闭环（出题 → 检索 → 评分 → 诊断 → 补知识 → 复测）**约 40 分钟**，跑 **5 个迭代 × 每轮 10 题**，合计 **110,357 token**（输入 96,561 / 输出 13,796，**74 次模型调用**）——调用分布是「答案生成 10 次/轮 + 出题 6 次/轮」。

两套真实跑过的场景（[usage.md](docs/usage.md)）：知识库迭代闭环、带质量回检的文档生成流水线。

## 我到底开源了什么（请如实看待）

- ✅ **开源**：完整的角色划分、8 份可直接复用的提示词、编排职责定义、安全阈值、失败模式手册；
- ❌ **没开源**：编排引擎 / 框架 / 运行时。本仓库**不能 `git clone` 之后跑起来**，它是一份"团队编制说明书"，不是一个产品；
- 🔒 **已脱敏**：提示词原本服务于一个具体的业务知识库（垂直领域文档），本仓库把业务对象泛化为「知识库 / 被测系统」；不含任何个人身份信息、密钥或第三方私有内容。
