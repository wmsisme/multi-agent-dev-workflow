# 使用示例：两个真实跑过的场景

## 场景 A：知识库迭代闭环（主力场景）

**目标**：让知识库问答系统自己发现"哪里不会"、补上、再验证。

```text
① 出题 Agent        产出 4 类 × 20 题，每题带「答案必须包含的关键点」
                     ↓（题目 + 关键点）
② 调用管控 Agent     按配置封装 N 轮检索-生成，逐轮记录评分与耗时
                     ↓（答案 + 检索到的上下文）
③ 评分 Agent        检索阶段：上下文相关性 / 召回
                    生成阶段：忠实度 / 答案相关性 / 关键词命中 / 标准答案吻合
                    输出 JSON：逐指标分 + 加权总分 + 评语
                     ↓（低于阈值的题 → 失败样本集）
④ 诊断 Agent        判定根因：检索到无关内容 / 遗漏关键信息 / 模型幻觉
                    给出证据定位 + 修正建议 + 「下一轮不该添加什么」
                     ↓（"遗漏关键信息" → 派给写入）
⑤ 写入 Agent        生成补充知识块 → 写前校验 → 分批写入 → 写后抽样检索验证
                     ↓（统计 + 验证结果）
⑥ 回到 ② 复测        对比同一批题的前后分数
```

**闭环成立的两个标志**：

1. **弱项收敛**：某个知识域的低分题数量明显下降（本编制在真实项目中把最弱域的低分题从 7 题压到 0）；
2. **题库自增长**：同一批题反复用会"过拟合"，所以要持续出题扩库。

**实测参考值**（一整轮闭环：出题 → 检索 → 评分 → 诊断 → 补知识 → 复测）：

| 指标 | 实测值 |
|---|---|
| 墙钟耗时 | **约 40 分钟** |
| 迭代轮数 | **5 轮**，每轮 **10 道题** |
| token 合计 | **110,357**（输入 96,561 / 输出 13,796），均值约 **22,071 / 轮** |
| 模型调用次数 | **74 次**（答案生成 10 次/轮 + 出题 6 次/轮；第 1 轮尚未出题，仅 10 次） |
| 单次调用上限 | **120 秒**超时 |

> ⚠️ **这三个数分属三个层级，别混成一个**：40 分钟是整轮墙钟、11 万 token 是整轮累计、120 秒是单次调用上限。
> 而且**报 token 时必须带上"每轮 10 题"**——否则"每轮 2.2 万 token"会被听成"一道题 2.2 万"，差一个数量级。
>
> 📌 **早期的运行并没有 token 统计**（那时只有轮次与评分）。后来意识到多 Agent 的调用次数比单 Agent 多一个量级、不记账就判断不出哪些 Agent 值得留，才补上按轮统计的 usage 记录。

**中途停止的判据**：见 [safety-guardrails.md](safety-guardrails.md) 的四道闸门——**跑不完没关系，但必须能干净地停下来并且拿到当前最好的结果**。

> ⚠️ **一个真实教训**：本编制早期没有做缓存与断点，一次系统卡死中断导致**已经翻译好的文档与已经向量化的结果全部归零**，几十分钟的活白做。之后补了两样：翻译按 commit 级缓存（同一段原文不重复翻译，重跑可直接接上）、向量化可续传（记录进度，重启接着走）。**长流程 Agent 系统里，"能跑"和"中断了也不丢活"是两件事。**

## 场景 B：带质量回检的文档生成流水线

**目标**：产出一份成体系的文档，并且**自动发现"掺了无关内容"**。

```text
① 编排 Agent        先出整体大纲 →（人工确认）→ 逐节派活
                     ↓
② 文档生成 Agent    按大纲逐节写，含目录 / 示例 / FAQ，
                    不确定的信息明确声明，不编造
                     ↓
③ 诊断 Agent        对照「用户要求」与「检索到的材料」复核：
                    - 有没有写进去但不该出现的内容（掺入无关信息）
                    - 有没有该写却没写的关键要求（遗漏）
                    - 有没有检索材料支持不了的论断（幻觉）
                    ↓ 不达标
④ 回到 ② 定向重写    带上下一条「不应添加什么」的反向约束
```

**这个场景里最值钱的一条经验**：长文任务的重写指令**必须包含反向约束**。只说"再补一些"，产出会一轮比一轮臃肿，最后重点被淹没。

## 把它接到你自己的框架上

这套编制的**唯一硬性要求**是运行时支持两件事：

1. **子 Agent 派发**（能把任务 + 材料交给一个独立上下文的 Agent，并拿到它的结果）；
2. **description 驱动的匹配**（编排器能读到"这个 Agent 何时该被用"）。

| 框架形态 | 接法 |
|---|---|
| 自带主 Agent + Task/子 Agent 机制 | 直接把 8 个提示词建成子 Agent，**先用框架自带主 Agent 当编排器** |
| 有工作流引擎（节点/图） | 把每个 Agent 建成一个节点，编排器建成"带条件边"的调度节点（返工 = 回到上一节点的边） |
| 手写代码编排 | 把提示词当 system prompt 用，调用管控那套阈值**落在代码里**（代码管兜底，提示词管判断） |

**裁剪建议**：先用 3 个 Agent（出题 → 评分 → 诊断）跑通一条最短闭环，确认"分数真的能让人做出决定"，再补写入与文档生成。一上来铺 8 个，调不通时你分不清是哪个环节坏的。
