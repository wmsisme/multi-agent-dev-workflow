# 架构与编排规则

## 一、整体数据流

```text
               ┌──────────────────────────────────────────────────┐
               │              主 Agent（编排器）                    │
               │  ① 需求分析  ② 列可用 Agent  ③ 拆子任务            │
               │  ④ 匹配 Agent  ⑤ 定序与依赖  ⑥ 按序调用             │
               │  ⑦ 收结果    ⑧ 整合  ⑨ 质量回检 → 不达标则返工      │
               └──────────────────────────────────────────────────┘
                                    │ 派活（只传必要材料）
        ┌───────────────────────────┼───────────────────────────┐
        ▼                           ▼                           ▼
  出题 Agent ──题目+关键点──▶ 评分 Agent ──分数+评语──▶ 诊断 Agent
                                                        │ 根因+修正建议
                                                        ▼
                                            知识库写入 Agent（补资料）
                                                        │ 写入统计+验证结果
                                                        ▼
                                                 回到「复测」（再评分）
```

**关键点**：诊断 → 补充 → 复测这段**接力**是自动闭环的核心。没有它，多 Agent 只是"把活拆开干"，有了它才是"能自己变好"。

## 二、四个设计原则

### 1. 职责单一（一个 Agent 只干一件事）

出题的不管评分，评分的不管补资料。原因很直接：**一个 Agent 既出题又评分，等于运动员兼裁判**——它会倾向于给自己打高分，而且标准答案也是它生成的，偏差会叠加。

### 2. 上下文隔离（每个子 Agent 独立上下文）

主 Agent 派活时，把**任务 + 它需要的材料**一起传过去；子 Agent 干完把结果交回来，**看不到别人的中间过程**。

好处有两个：
- **省上下文**：长流程里上下文是线性膨胀的，隔离后每个 Agent 只看自己那一段；
- **防污染**：评分 Agent 如果看到了出题 Agent 的完整思路，会被带偏。

代价是：**跨 Agent 要传的东西，必须由主 Agent 显式搬运**。这一点在设计派活逻辑时最容易被忽略——忘了搬，下游 Agent 就会"凭空判断"。

### 3. 工具边界（每个 Agent 声明可用工具）

每个子 Agent 在配置里声明自己能用的工具清单。作用：

- 压缩行为空间（不能用的工具它就不会尝试）；
- 限制爆炸半径——**写入类 / 命令执行类工具只给该给的 Agent**；
- 降低误派任务造成的破坏。

### 4. 控制流由模型决定（而不是写死的 Prompt 链）

固定 Prompt 链是死的：第 4 步无论结果好坏都会走到第 5 步。
这里的控制流在**运行时**决定：评分不过关 → 返工或换 Agent；诊断出"检索遗漏" → 派给写入 Agent 补资料 → 回到复测。

**编排器的职责不是"按顺序发消息"，而是"读结果、做判断、决定下一步和要不要返工"。**

## 三、Agent 之间的接口约定

要让编排器能"读懂"上一步，每个 Agent 的输出必须是**结构化的**：

| Agent | 输出必须包含 |
|---|---|
| 出题 | `问题` + `关键点清单`（可逐条核对） |
| 评分 | `scores`（逐指标分 + 评语）/ `total_score` / `overall_comment`，JSON |
| 诊断 | `根因分类` + `证据定位` + `修正建议` + **`下一轮不应添加的内容`** |
| 写入 | `成功/失败/更新条数` + `抽样检索验证结果` + 待用户裁决的冲突 |
| 调用管控 | `result` + `monitor{iterations, elapsed, score_history, interrupt_reason}` |

**通用铁律**：Agent 之间不要用自然语言长段互相沟通，用**固定字段**。否则编排器每一步都要去"理解"上一步，既贵又不稳。

## 四、什么时候不该用多 Agent

多 Agent 有明确的成本：调用次数增加、编排复杂度上升、失败面变大。以下情况**别用**：

- 任务步骤固定、结果确定（写个脚本更便宜也更快）；
- 单步任务能一次做完（拆开只会增加出错机会）；
- 没人能给"什么样的产出算合格"下定义（没有验收标准，编排器无法判断要不要返工）。

**判断标准一句话**：这个任务里，**下一步该做什么取决于上一步的结果**——是，则用多 Agent；否，则用脚本或单 Agent。
