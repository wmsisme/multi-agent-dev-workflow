# FAQ / 常见质疑

## Q1：这不就是写好的几个 Prompt 顺序调用吗？

区别在**谁决定顺序、要不要返工**。

固定 Prompt 链是死的：第 4 步无论结果好坏都会走到第 5 步。这里是**运行时决定**的——评分不过关，编排器安排返工或换 Agent；诊断出"检索遗漏"，它把任务派给写入 Agent 补资料，然后回到复测。

**检验方法**：把某一步的输入换成一份明显不合格的结果，看系统接下来怎么做。回答"照常往下走"的是 Prompt 链，回答"退回重做/改派"的才是编排。

## Q2：为什么不干脆写个脚本？

脚本能算分数、能批量调用，但**算不了"为什么失败"**——"检索到无关内容 / 遗漏 / 幻觉"是语义判断，写成 if-else 写不动。
反过来，**阈值、计数、超时这些必须落在代码里**：提示词管判断，代码管兜底。两者不是替代关系。

## Q3：为什么不直接用 LangGraph / AutoGen 这类框架？

可以用，而且如果只是要跑通流程，用框架更快。这套编制的定位不同：

- 它给的是**角色划分 + 提示词 + 编排职责 + 安全阈值**，这部分和框架无关——换任何框架，这三件事都是最核心的；
- 它**不绑定运行时**：本仓库里没有一行引擎代码，你可以把它落到任意支持子 Agent 派发的框架上。

## Q4：8 个 Agent 是不是太多了？

数量本身不是目标，**边界清不清楚**才是。判断标准：

- 每个 Agent 能不能用一句话说清"它只干什么"？
- 相邻两个 Agent 的职责有没有重叠（重叠 = 会互相推诿或重复劳动）？
- 有没有哪个 Agent 的产出**没人消费**（没人用 = 该删）？

本编制里 `rag-controller`（调用管控）和 `generate-score`（评分）看起来像，但一个是**过程指标**（轮次/耗时/趋势），一个是**质量指标**（相关性/忠实度），服务对象不同，所以保留为两个。

## Q5：怎么知道多 Agent 真的比单 Agent 好？

用同一批题、同一套评分标准，跑两种配置，比三个数：

1. **总分**（谁高）；
2. **方差**（跨轮次分数稳定性——多 Agent 的主要收益往往在这里，而不是总分）；
3. **单题成本**（token + 时间）。

如果总分没差、方差也没差，那就说明你的任务里"下一步不依赖上一步结果"——**该退回单 Agent 或脚本**（见 [architecture.md](architecture.md) 第四节）。

## Q6：Agent 会自己骗自己吗？

会，这是已知瓶颈，尤其在"同一个 Agent 既生成又评分"时。本编制的对策：

- 出题 / 评分 / 诊断**拆成三个 Agent**，彼此上下文隔离；
- 忠实度不靠笼统打分，改成**基于关键点逐条独立检索 + reranker 交叉打分**；
- 长期正解是接一条**人工标准答案队列**做校准。

## Q7：这套东西能直接跑吗？

**不能。** 本仓库不含编排引擎或运行时，它是**编制说明书**（提示词 + 边界 + 规则 + 阈值），不是可执行产品。落地方式见 [usage.md](usage.md) 最后一节。

## Q8：提示词是中文还是英文？

原编制里混用：编排、调用管控、知识写入、角色转换用中文；评分、诊断、出题、文档生成用英文。
经验：**判分和诊断这类要求"严格按标准输出"的任务，英文提示词约束力更稳**；面向中文用户的产出任务用中文更自然。你可以按自己的模型统一语言，改语言不影响结构。
